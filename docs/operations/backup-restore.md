# バックアップと復旧（手順書）

実データを扱う環境（Supabase Mode）の取得対象・頻度・復旧の手順。Demo Mode（架空のデータ・インメモリ）は対象外。
画面に「最終バックアップ日時」は出さない（アプリから確かめられない値を推測で出さない）。

## 1. 取得対象

| 対象           | 内容                                                                 | 取得の手段                                                                       |
| -------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| データベース   | 全テーブル（監査ログ・追記専用の版を含む）                           | Supabase の自動バックアップ（プランの機能）。必要に応じて論理ダンプ              |
| Storage の実体 | 資料・原本・出力・返却用の書き出し                                   | データベースのバックアップに含まれない前提で、別に取得する（提供元の仕様を確認） |
| 構成           | マイグレーション・アプリの版（コミット）・環境変数の一覧（値は除く） | リポジトリと運営の作業記録                                                       |

## 2. 頻度と目標（合意値の欄）

| 項目                       | 合意値     | 備考                                                                                                           |
| -------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------- |
| データベースの取得の頻度   | （未合意） | 提供元のプランで決まる                                                                                         |
| Storage の実体の取得の頻度 | （未合意） |                                                                                                                |
| RPO（失ってよい時間）      | （未合意） | 判断事項 D18                                                                                                   |
| RTO（復旧までの時間）      | （未合意） | 判断事項 D18                                                                                                   |
| 保存期間                   | （未合意） | データ取扱条件（設定の「データの取扱い」）と揃える                                                             |
| バックアップの残存期間     | （未合意） | 削除の後もバックアップに残る日数。データ取扱条件の「バックアップの残存期間」（`backup_residual_days`）と同じ値 |

合意したら、この表と設定の「データの取扱い」の版を同時に更新する。
バックアップの残存期間は、使う提供元の保存期間（データベースのバックアップ・ポイントインタイムリカバリ・ログ）のうち
最も長いものに余裕を足して決める（提供元・プラン・設定で変わるので、契約前に公開資料で確かめる）。
この日数は削除の記録（`tenant_lifecycle_records.backup_residual_days`）と消去の見込み日、顧客への削除完了の報告に入る。

## 3. 復旧の手順（別のプロジェクトへ）

1. 新しい Supabase プロジェクトを用意する（本番の公開 URL の環境には接続しない）。
2. マイグレーションを番号順に適用する（`supabase db push` など）。
3. バックアップ（または論理ダンプ）からデータを戻す。追記専用の表のトリガは、戻す作業の間だけ所有者のロールで扱う。
4. Storage の実体を同じパスへ戻す。
5. 確かめる:
   - 件数: 直近の全データの書き出し（返却用）の `manifest.json` の表ごとの行数と、戻した DB の自社の行数を比べる。
   - 実体: 書き出しの `files` の sha256 と、戻した Storage の実体の sha256 を比べる。
   - 権限: `pnpm verify:supabase` はデモの Fixture を前提とするため、ローカルの検証環境（`supabase start`）で
     同じ版のマイグレーションに対して流し、RLS が効くことを確かめる（実データの環境には流さない）。
6. アプリの接続先を切り替える前に、企業の管理者がログインして主要な画面（ホーム・データ・開示プロジェクト・監査ログ）を確かめる。
7. **復旧点より後に終了したテナントを、もう一度終了処理する**。バックアップは終了処理の前の状態を含むため、
   戻すと削除したテナントのデータも戻る。元の環境の削除の記録（`tenant_lifecycle_records` の `executed_at` が
   復旧点より後のもの）を一覧にし、該当するテナントごとに `docs/operations/tenant-offboarding.md` §2〜§4 を
   もう一度行う（戻した DB の組織コードで確認コードを合わせる。残存期間は元の削除の記録の値を使う）。
   顧客への削除完了の報告は改めて出さず、運営の作業記録に「復旧に伴う再削除」として残す。
   戻した Storage の実体も同じく消す。再削除が済むまで、接続先を切り替えない。

## 4. 復旧の訓練

- トライアル中に 1 回以上行う（既定は 2 月。判断事項 D18）。
- トライアルの評価のシナリオ（テーマ「運用」）として、実施日時・所要時間・結果・問題点を記録する。
- 訓練では架空のデータか、合意した範囲の書き出しだけを使う。
