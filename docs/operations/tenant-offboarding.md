# テナントの終了（返却と削除）の手順書

トライアルの終了・契約の終了のときに、合意した扱い（継続移行／返却／削除）に従って行う。
削除は**取り消せない**。返却の受け取りの確認と、保証側の記録の扱いの合意が済むまで行わない。

削除の後も、データはバックアップに通常の保存期間（データ取扱条件で合意した**バックアップの残存期間**）残る。
期間の終了後に消え、それまで秘密情報として管理する（復元その他の目的に使わない）。顧客には「削除完了の報告」で
削除日と消去の見込み日（削除日＋残存期間）を渡す（§4・§6）。

## 1. 返却（企業の管理者が行う）

1. 企業の管理者が、設定の「データの取扱い」→ 見出しの「その他」→「全データを書き出す（返却用）」で書き出す。
   - 「データ」: 表ごとの CSV（UTF-8 BOM）＋ `manifest.json`（表・行数・sha256・生成者・アプリの版）＋ `README.md`
     （README に「削除の後のバックアップ」の固定の文。合意した残存期間の日数入り）
   - 「資料の実体」: アップロードした資料のファイル（実体の無い資料は manifest の `missingFiles`）
   - 監査法人の調書・案件の記録・全テナント共通のマスター・利用者ごとの通知は含まない（理由は manifest の `excluded`）
2. 受け取った側が各ファイルの sha256 を計算し、manifest の値と一致することを確かめる（README に方法）。
3. 受け取りの確認（日時・確認者・manifest の sha256）を運営の作業記録に残す。

## 2. 削除の前の確認（運営）

- 保証側の案件が残っていないこと。残っている場合は、保証人と合意した扱い（保証側の記録の保存期間など）に従う。
  削除の関数は案件が残っていると止まる。
- 監査ログの扱い（既定は残す。判断事項 D8・D17）が合意どおりか。
- **バックアップの残存期間**（データ取扱条件の最新の版の「バックアップの残存期間」）が合意済みか。
  未合意なら、合意した日数を `--backup-residual-days` で渡す（スクリプトは日数が無いと止まる。推測で見込み日を出さない）。
  合意値と違う日数を渡すと止まる（先に条件の版を記録し直す）。終了処理でデータ取扱条件も消えるので、**削除の前に読む**。
- 事前確認のスクリプトで、表ごとの件数を確かめる（**何も削除しない**）:

```bash
pnpm exec tsx scripts/offboard-tenant.ts --org-code <組織コード> \
  --manifest-sha256 <返却 manifest の sha256> --executed-by "<実行者の表示名>" \
  [--backup-residual-days <日数>] [--executed-on <YYYY-MM-DD>] --confirm-project <ref>
```

スクリプトは、DB の所有者が実行する SQL と「削除完了の報告（案）」を表示する。`--executed-on` は SQL を実行する日
（日本時間。省略すると今日）。

## 3. 削除（運営・DB の所有者のロール）

事前確認のスクリプトが表示した SQL を、DB の所有者のロールで実行する（Supabase の SQL エディタなど）。

- `t4d.offboard_organization(org_id, confirm_code, manifest_sha256, executed_by_label, backup_residual_days)`
  （0060 の 5 引数版）は所有者だけが実行できる（`authenticated`・`anon`・`service_role` から EXECUTE を剥奪）。
  旧い 4 引数版（0058）も使えるが、残存期間は未合意（null）として記録される。
- 確認コード（組織コード）が一致しないと止まる。企業テナントだけが対象。残存期間は 0〜400 日。
- 関数の中でだけ、追記専用の表（監査の記録など）の削除を許す。利用者が同じ設定を立てても越えられない。
- 組織の行は外部キーの参照先として残すが、**匿名化する**（名称は「終了した組織」、正式名は空、コードは
  `offboarded-` ＋組織コードのハッシュの先頭 12 桁。0060）。顧客の名称を DB とバックアップの新しい世代に残さない。
- `tenant_lifecycle_records` に削除の記録（組織コードのハッシュ・表ごとの件数・返却 manifest の sha256・実行者・日時・
  **バックアップの残存期間・消去の見込み日**。顧客の内容は持たない）を 1 件残す。
- `storage_access_events`（資料へのアクセスの記録）は削除の対象の表から外しているが、資料の版（`file_versions`）の
  削除に**連鎖して消える（残らない）**（`tests/rls` の終了処理のテストで確認。関数のコメントも同じ）。
  終了後も残す必要がある場合は、外部キーの変更が要る（判断事項 D9。別途）。
- 監査ログ（`audit_events`）は組織の列を持たないため消えない（既定どおり残す。判断事項 D8）。保存期間は契約に書く。

## 4. 削除の後（運営）

1. Storage の実体を消す: `evidence-private`・`enterprise-originals-private`・`exports-private`・`tenant-exports-private` の
   `<…>/<組織 ID>/…` のパス（バケットごとのパスの形は `docs/storage-model.md`）。
2. その組織にしか属していない Auth ユーザーを消す（他の組織にも属する人は消さない）。
3. 削除の記録の ID・実行日時・件数・消去の見込み日（`backup_purge_due_on`）を運営の作業記録に残す。
4. **削除完了の報告を渡す**: スクリプトが表示した「削除完了の報告（案）」の件数・日付を、削除の記録
   （`tenant_lifecycle_records` の `table_counts`・`executed_at`・`backup_purge_due_on`）と照らして確定し、顧客へ渡す。
   報告には組織の名称を入れない（組織コードと日付・件数だけ）。内容: 削除の実施日・削除した行数・返却 manifest の
   sha256・バックアップの残存期間・消去の見込み日・それまで秘密情報として管理すること。

## 5. ロールバック

削除は取り消せない。誤りに気付いたら、返却した書き出し（manifest で整合を確かめたもの）から別のプロジェクトへ戻す
（`docs/operations/backup-restore.md` の復旧手順）。関数そのものの戻し方は `docs/known-limitations.md` §6。

## 6. 消去の見込み日の後（運営）

1. 消去の見込み日（削除の記録の `backup_purge_due_on`）を過ぎたら、使っている提供元のバックアップの保存期間
   （データベースのバックアップ・ポイントインタイムリカバリ・ログなど）を過ぎたことを、提供元の画面か公開資料で確かめる。
2. 確かめた日・確かめた方法・確認者を運営の作業記録に残す（顧客から求めがあれば、その記録を示す）。
3. その間にバックアップから復旧した場合は、`docs/operations/backup-restore.md` §3 の手順 7（復旧点より後に終了した
   テナントの再終了処理）を行ったことも記録する。
