### 修正後の検証について（正直な記載）

フェーズ 8 の修正が新たな欠陥を生んでいないかを **サブエージェントによる独立監査**でも
確かめようとしましたが、セッション上限により 4 エージェントすべてが実行前に停止しました。
したがってその独立監査は**未実施**です（「所見 0 件」は「問題なし」を意味しません）。

代わりに、同じ検証項目を QA 担当者自身が実行しました。実施内容と結果:

- **service-role 経路の限定**: `getInvitationAcceptDb` の呼び出しは招待ページと受諾アクションの 2 箇所のみ（Grep で全数確認）。
  受諾で付与されるロール・組織は招待レコードの値のみを使用。`ensureAuthUser` が受け取るメールは招待レコードの値のみ。
- **前年比照合の退行**: boundary は「連結」32 件（FY2025/FY2026）と「内部取引」2 件（FY2026）のみ。
  照合キーに boundary を足した後も正当な 32 件は一致を維持し、消えたのは内部取引由来の誤警告だけ（実データで確認）。
- **リンク検証**: 13 種の攻撃形（`..`・`%2e%2e`・二重エンコード・バックスラッシュ・NUL・改行・`javascript:`・`//host`）と
  5 種の正当形を実行して確認。**正当なリンクを誤って弾く不具合（BUG-049）を発見し修正**。
- **CSP 注入**: origin は `new URL().origin` で正規化され、パス・セミコロン・改行は落ちる。
  http/https 以外を弾く処理を追加。
- **コメント権限**: `enterprise.disclosure.read` 保有ロールを列挙し、UI 導線（write 権限）との差を確認。
  設計どおりであることを `docs/known-limitations.md` S-14 に明文化。
- **遷移コメント**: 空白のみの入力で例外になる退行（BUG-050）を発見し修正。

この自己検証で見つかった 2 件は修正し、回帰テストを追加しています。

## 5. 主要な発見

### 5.0 フェーズ 8 の独立検収が発見した Critical（2 件・修正済み）

実装・修正を担当していない別サブエージェントに、結論を信用させずに独立検収させました。
その結果、**私（QA 担当）が見落としていたテナント分離の穴が 2 件**見つかりました。

| ID                      | 内容                                                                                                                                         |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **BUG-029（Critical）** | 他テナントの Evidence を `fileVersionId` 指定で取得できた。無関係な企業・監査法人が他社の機密 Evidence へ到達できる状態だった                |
| **BUG-030（Critical）** | 他法人の Issue・レビュー Note を Server Action で書き換えられた。**Sign-off の抑止条件を外部から解除**でき、被害側の監査ログに痕跡も残らない |
| BUG-031（High）         | 他社の許諾（Grant）を取り消せた                                                                                                              |

**なぜ私の監査で見つからなかったか**：`robustness-audit.spec.ts` は `/api/files/signed-url` を
**存在しない UUID** でしか試しておらず、「**実在するが他人のもの**」という最も重要なケースを
突いていませんでした。Server Action も、正しい ID での実行しか検証していませんでした。
「画面にボタンが無いこと」と「API から実行できないこと」は別物である、という原則の適用が
私自身の側で不十分でした。

**根本原因**：Demo Mode の `DbClient` に行レベルの防御が無く（`findById` は単なる配列検索）、
アプリ層の明示チェックだけが頼りである一方、そのチェックがファイル取得経路と 3 つの Server Action で
欠落していました。Supabase Mode は RLS が救いますが、**本番は Demo Mode で動いている**ため実害がありました。

3 件とも修正し、`tenant-isolation-audit.spec.ts`（5 件）で回帰を固定しました。
**負の対照**（認可を一時的に外すとテストが落ちること）も確認済みで、
「常に拒否」で通ってしまう空テストではありません。
