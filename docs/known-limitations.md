## 2. Demo Mode 固有

| #   | 制約                                                                                                    |
| --- | ------------------------------------------------------------------------------------------------------- |
| D-1 | データはサーバープロセスのメモリ上にあり、**再起動で初期状態へ戻る**                                    |

D-2 の例外（2026-09-29 追記）: 開示優先モードの架空資料 3 点（`src/lib/fixtures/disclosure-documents.ts`）は、
引用・前年比較の題材として本文を見せる必要があるため、Demo Mode のストレージが定義から本文テキストを生成して返す
（再起動後も同じ内容）。Supabase Mode の seed にはこれらの実体も無い（他の Fixture ファイルと同じ）。

### D-3 の実害と緩和策（2026-08-20 追記）

本番（Vercel の Demo Mode）で実操作を検証したところ、インスタンスをまたぐと
「保存したのにリロードで消える」「取込直後のジョブ画面が 404 になる」
「Copilot の回答が表示されない」が起きていた。恒久制約により外部ストアは使えないため、
次の 3 段構えで緩和している。

1. `vercel.json` で `regions: ["hnd1"]` を指定し、インスタンスの分散を抑える。
2. `src/lib/repositories/demo-persistence.ts` が、人の操作（評価・コメント・値編集・小さな取込）を
   **変更のあった列だけ** Cookie（httpOnly・約 3.8KB 上限・8 時間）に控え、読み取り時に Fixture へ再適用する。
   上限を超えた分は古い操作から捨てる。
3. Copilot のように「作った直後に見せる」ものは、リダイレクトせず Server Action の戻り値で描画する。

取込のプレビューは **ブラウザの sessionStorage（数 MB）** で持ち回す（2026-08-24 変更）。
投入時に Server Action が解析まで終わらせてプレビュー内容を返し、タブが預かる。
確定時はフォームが期間と元資料の位置も一緒に送るため、確定のリクエストが
ジョブを持たないインスタンスへ届いても台帳へ反映できる。

| 一括取込        | 本番 Demo Mode     | ローカル Demo Mode | Supabase Mode  |
| --------------- | ------------------ | ------------------ | -------------- |
| 50 ファイルまで | 動く（本番で実測） | 動く               | 動く           |
| 51 ファイル以上 | 件数付きで拒否     | 件数付きで拒否     | 件数付きで拒否 |

開示優先モード（2026-09-29 追記）の表は、状態・ポインタ・短文だけの小さい表
（プロジェクト・適用判断・定性情報の台帳・節・レビュー依頼と記録・コメント・再確認・KPI 目標・機能設定）を Cookie で持ち回す。
~~本文の版・引用位置・スナップショット・標準 CSV の取込バッチは同一インスタンスのメモリにだけ残る~~ →
**2026-09-30 に変更**: 小さくした形で Cookie に載せる（下の「別インスタンスでも実演の流れを続ける」）。
節の自動保存本文（`working_body`）は引き続き Cookie へは載せない（操作はすべて画面の本文を送る。下の節を参照）。
別インスタンスで参照先の版が無い場合（押し出し・別のブラウザ）、画面は「見つからない」として安全に失敗させる。

開示本文の AI 下書き（`ai_runs` の `disclosureBlockDraft`）は、候補（`output_json`）と許可リスト・土台の本文ハッシュ
（`input_reference_ids`）の両方が別インスタンスでの採用に要るため、列を削らずに Cookie へ載せる（2026-09-29 決定）。
実測で根拠 3 件の実行は Cookie 上 約 2.2KB（2 チャンク 約 7.6KB の約 3 割）、根拠 9 件で 約 3.5KB。
数回生成し直すと、他のデモ操作（レビューの記録など）が古い順に押し出される。1 件が 1 チャンク（約 3.8KB）を
超える実行は Cookie に載らず、実行したインスタンスのメモリにだけ残る。
確認を終えた（採用・破棄した）実行は、別インスタンスでの採用が要らないため、Cookie では候補の本文と段落の指紋を省く
（2026-09-30 自己監査 第 3 回。下の節を参照）。

#### 自己監査（2026-09-29）で足した Cookie の規則と、残る制約

- Fixture DB はインスタンスの全利用者で共有されるため、Cookie から戻すレビュー依頼・レビューの記録・節の状態は
  **DB のトリガと同じ規則（職務分離・状態遷移・承認の記録の有無）を通したものだけ**を適用する
  （`applyDemoEdits` の `acceptEdit`）。追記専用の表（レビューの記録・再確認の判断・KPI 目標）は既存行を書き換えない。
- Cookie の容量が足りないときは、機能設定（開示優先モードの ON/OFF）以外の古い編集から押し出す。押し出しが起きたら
  ヘッダーに「古い操作の一部を保持できませんでした」と示す（`t4d.demo-evicted`）。~~出力記録（`export_artifacts`）は Cookie に載せない~~
  （2026-09-30 から小さくして載せる。下の「別インスタンスでも実演の流れを続ける」）。
- **残る制約**: レビューの記録が押し出された後に、依頼・節の承認だけが別インスタンスへ届くと、規則を満たせず適用されない
  （そのインスタンスでは承認前の状態に見える）。同じインスタンスのメモリには残る。
- 開示デモのリセットは `t4d.demo-reset` Cookie に「どの組織を・いつ」戻したかを残し、別インスタンスでも次のリクエストで
  同じ範囲を Fixture の初期値へ戻す。**残る制約**: 印は組織ごとに最新の 1 件だけで、別の組織のリセットが続くと先の印は上書きされる。
- 以前のデプロイの Cookie に残った Data Point の行（値の区分・値の有無の列が無い）は、0039 の backfill と同じ既定で補ってから適用する。

#### 自己監査 第 2 回（2026-09-29）で変えた Cookie の規則

- 追記専用の表に数値の版（`data_point_versions`）と適用判断（`project_framework_decisions`）を足した。
  Cookie から既存の行（承認済みの版の値など）を書き換えられない。新しい行の追加は従来どおり。
- レビューの記録は、依頼で指名したレビュー担当・最終承認者のものだけを戻し、依頼の状態に合わない記録
  （差し戻して終わった依頼への承認など）は戻さない（0042 のトリガと同じ規則）。節の承認は「承認で終わった依頼」の版だけ。
  依頼の編集が押し出されて対応する依頼が無い「レビュー依頼中」「承認待ち」「差戻し」の節は、状態だけを下書きに戻して
  ほかの変更（現在の版・題名・担当）は戻す（取り下げる依頼が無いまま編集できなくなるのを防ぐ）。
- Cookie のチャンクは、古い順に**空きのあるチャンクへ**詰める（以前は先頭から入るだけを前のチャンクに入れ、
  大きな AI 下書きの後の編集がすべて 2 つ目に回り、1 つ目に 1KB 以上の空きを残したまま押し出していた）。
  チャンクをまたいだ順序は編集ごとの追記番号（`n`）で戻し、押し出しは引き続き古い編集から。
  （2026-09-30 に、全部を 1 本に圧縮してからチャンクに切り分ける形式へ変えた。下の節を参照）
- 押し出しの知らせ（`t4d.demo-evicted`）は、押し出した表の名前を持つ。開示デモのリセットで開示の表の知らせを、
  ログアウトですべての知らせを消す。取込の行（`ingestion_rows` など）どうしの押し出しでは知らせない
  （第 3 回で「同じ取込の行どうし」に限った。下の節を参照）。
- 開示デモのリセットの印（`t4d.demo-reset`）は「時刻-乱数」の世代を持ち、インスタンスは**反映済みより新しい印だけ**を
  反映する（起動より前の印は反映しない）。以前は乱数だけで新旧を比べられず、2 つのブラウザの印が交互に届くと、
  リクエストのたびに開示デモを戻し合っていた。以前の形式（時刻なし）の印は反映しない。
- リセットの印は署名の無い Cookie のため、**ログインした利用者の組織が印の組織と同じで、開示の編集権限
  （リセットの操作と同じ `enterprise.disclosure.write`）を持つとき**に `getSession` が反映する（以前は `getDb` が
  ログイン前に反映しており、誰でも任意の組織のデモ状態を消せた）。**残る制約**: 閲覧だけの利用者がほかのインスタンスへ
  先に届いた場合、そのインスタンスは編集権限のある利用者が来るまでリセット前の状態を見せる。
- リセットは、このインスタンスが規則に合わず受け付けなかった開示の編集（押し出しで孤立した記録など）も Cookie から取り除く。
- 開示のレビューの通知（依頼・差戻し・承認の知らせ）は、本文（`body`）を空にして Cookie へ載せる。別インスタンスでも
  題名とリンクで届き、ベルの件数に数える（以前は載せず、「通知しました」と表示したのに別インスタンスでは届いていなかった）。

#### 自己監査 第 3 回（2026-09-30）で変えた Cookie の規則

- Cookie のチャンクを 2 → **3 つ（約 11.4KB）**にした。実演の流れ（Scope3 → 標準 CSV → 定性 → AI 下書き → レビュー・承認 →
  草稿 → KPI 目標）の後半で、前半の取込の数値が押し出されていた。ほかの Cookie・ヘッダーを足しても Node の既定の
  リクエストヘッダーの上限（16KB）に収まる。4 つ以上にはしない。
- 確認を終えた（採用・破棄した）原稿の AI 下書きの実行は、Cookie では候補の本文（`output_json`）と段落の指紋を省く
  （メモリの行は全体を持つ）。別インスタンスでは確認済みの実行として一覧に出るが、候補の本文は表示しない
  （採用した段落は本文の版に残っている）。確認中の実行は従来どおり全体を載せる。
- 押し出しの知らせを出さないのは、**同じ取込の行どうし**の押し出しだけにした。取込ジョブ・ファイルの行や、
  別の操作・別の取込による取込の行の押し出しは知らせる（以前は押し出された表だけを見て、原因を問わず黙っていた。
  取込の画面にその案内は無かった）。
- Data Point の行は、現在の版（`current_version_id`）がその Data Point の版で、値の列（値・単位・区分・値の有無）が
  その版の写しのときだけ戻す。承認済みにする変更は、承認者の権限（`enterprise.data.approve`）と、承認の道筋がある
  Data Point では最新の巡の全段階の承認が要る（`transitionDataPoint` と同じ）。状態の変更は DB のトリガと同じ権限を求める。
  新しい数値の版を「承認済み」として足させない。
- 基準の適用区分（`project_frameworks`）は、現在の判断（`current_decision_id`）がその基準の判断で区分が同じときだけ戻す。
  判断なしで「適用・任意適用・対象外」を名乗らせず、古い判断へ戻させない。判断の記録は開示の編集権限を持つ人のもので、
  番号が前の判断より後のときだけ足す。
- 開示優先モードの切替（`organization_feature_settings`）は、更新者がその組織の管理者（`enterprise.org.manage`）のときだけ戻す。
- 「依頼中」の依頼を持つインスタンスへ、レビュー完了を経ずに「承認済み」「差戻し（最終段）」が届いても、同じ版の
  レビュー完了の記録があれば「レビュー完了」として扱って進める（Cookie は依頼を最新の 1 行にまとめて持ち回すため、
  途中の状態が届かない）。記録が無ければ進めない。
- リセットの基準時刻は、`getDb` が Cookie の操作をメモリへ適用する**前**に決める（以前はログイン後に印を見たときに初めて
  決めており、ログイン画面で前のリハーサルの操作を適用した後の時刻が基準になって、その後のリセットを反映しなかった）。
- リセットの印の時刻が現在より 5 分以上先なら反映しない（署名の無い印で遠い未来を名乗り、以後の本物の印を止めさせない）。
  **残る制約**: 印は署名していない（デモ環境は環境変数を持たないため、インスタンス間で共有する秘密鍵を置けない）。
- 開示デモのリセットで「数値データも初期値へ戻す」を選ぶと、Data Point と版・Data Point の承認の記録・承認の道筋・
  検証結果・標準 CSV の取込も同じ方法で戻す（数値の入力権限も要る）。別インスタンスへは印（`…:data`）で伝える。
  既定（選ばない）では従来どおり数値データに触れない。
- 出力タブの「スナップショット No.N を作成しました」は、そのスナップショットが一覧にあるときだけ出す（無ければ、別の
  サーバーで作成された可能性と作り直しを案内する）。出力のリンクで見つからないときは JSON の 404 ではなく、出力タブへ
  戻して理由を示す（他テナントの ID と同じ文言）。

#### 別インスタンスでも実演の流れを続ける（2026-09-30・本番での失敗への対応）

**経緯**: 2026-09-30 に本番（Vercel Fluid compute・Demo Mode・環境変数なし・DB なし）へ
`tests/e2e/zz-disclosure-project.spec.ts` を流したところ（`E2E_BASE_URL=https://terrast-t4d.vercel.app`）、2 手目で止まった。
標準 CSV の「検証」と「登録を確定」が別のインスタンスに届き、検証結果（取込バッチ）が最初のインスタンスのメモリにしか無く、
確定が「検証結果の有効期限が切れました」になった。同じ種類の失敗は、インスタンスのメモリにだけ置いていた行
（原稿の版・定性情報の版・引用位置・スナップショット・取込バッチ・作業本文）と、別の関数（別の経路）で読むものすべてで起きうる。

**最悪の場合の再現**: `T4D_DEMO_FRESH_FIXTURE_PER_REQUEST=1` でサーバーを起動すると、`getDb()` がリクエストごとに
Fixture を作り直し、Cookie の操作だけを適用する（`src/lib/repositories/demo-fresh-fixture.ts`）。すべてのリクエストが起動直後の
別インスタンスに届いたのと同じで、Cookie とブラウザが持ち回した状態だけが残る。`E2E_PORT=3219 pnpm test:e2e:stateless`
（`playwright.stateless.config.ts`）がこの切替で起動し、実演の流れ（`zz-disclosure-project`）・読み取りの導線
（`disclosure-first-nav`）・作業本文の控え（`editor-draft-restore.stateless.ts`）を、1 つのブラウザの Cookie を最後まで
持ち回して流す（実演の発表者と同じ。アプリのログイン・ログアウトは操作の記録を消さない）。**切替は Vercel に設定しない**
（本番は環境変数を持たない。未設定なら従来どおりプロセス共有の Fixture）。Service の層の同じ流れは
`tests/integration/stateless-demo-chain.test.ts` が手順ごとに Fixture を作り直して確かめる。

**Cookie の形式**: 上限（3 チャンク × 3,800B）は変えず、すべての編集を 1 本の JSON にして **Brotli（品質 9）**で圧縮し、
上限ごとに切り分ける（目印 `3`）。以前の形式（Cookie ごとに辞書化＋deflate、目印 `2`）も読む。実演の流れの終わりの
編集 47 件で、以前の形式の 3 分割は 11.2KB（前半の取込が押し出された）、1 本の辞書化＋deflate で 10.0KB、Brotli で 8.4KB。

**実測**（`pnpm test:e2e:stateless`、2026-09-30）: 操作の記録の Cookie は手順ごとに A01 224B → CSV・承認 2,135B →
定性情報 2,913B → 原稿・依頼 5,771B → 差戻し・承認 6,668B → 確定・DOCX 8,269B → 訂正・再確認 **8,640B（最大）**、
Cookie ヘッダー全体の最大 **8,788B**（上限の目安 13KB・Vercel の 1 ヘッダー 16KB・Node の既定 16KB に収まる）。押し出しなし。

**残る制約**

- 押し出しは従来どおり古い操作から。実演の流れを何周も続けたり大量の取込をしたりすると、前半の版・記録が押し出される。
  版が押し出されると、それを対象にしたレビューの記録（職務分離を版の作成者で確かめるため、版が戻るまで受け付けない）と、
  それを固定したスナップショットは別インスタンスでは戻らない（同じインスタンスのメモリには残る）。
- スナップショットは、固定した元の行（版・数値の版・社内コメント・資料の名前と区分・節の名前・指標名）が後から変わると
  作成時と同じ写しに組み立て直せず、別インスタンスでは「見つからない」になる（同じハッシュで別の内容を出さないため）。
- 手動の抜粋（`extracted_fragments`）・アップロードした資料の実体は持ち回さない。手動の抜粋から作った引用位置は別インスタンスで戻らない。
- 途中で失敗した確定（一部の行だけ書いた）を別インスタンスで続けると、検証し直した結果が確認したものと違うため競合で止まる
  （二重には書かない。もう一度検証してから確定する）。確定の控えが押し出された後に同じ確定を送り直した場合も同じく
  競合で止まる（最初の結果を示す代わりに、書いた後の台帳との差分を示す）。
- 1 件で 1 チャンク（3.8KB）を超える行（節の多いプロジェクトのスナップショットの目録など）は載せず、同じインスタンスのメモリにだけ残る。
- 作業本文の控えは**同じタブ**の sessionStorage にだけある（別のタブ・別のブラウザ・タブを閉じた後は戻らない。版として保存すれば残る）。
  控えを戻すのは、作業本文を最後に自動保存したのが本人だとサーバーが示すとき（`working_updated_by`。Cookie で持ち回し、
  版の保存・レビュー依頼・開示デモのリセットで消える）だけ。示さない控えは戻さずに消す（リセット前のリハーサルの入力を戻さない）。
  AI 候補の採用でサーバーが保存した本文も控える。
- 承認済みスナップショット（確定版）は、**報告範囲を変えた後は、変える前に確定したものを別インスタンスで戻さない**
  （「見つからない」）。Cookie には範囲を変えた日時が残らず、目録が名乗る固定時点の範囲の番号を確かめられないため、
  プロジェクトの今の番号で再確認の有無を見る（偽の目録で番号 0 を名乗って再確認を外させない）。同じインスタンスのメモリには残る。
- 偽の Cookie への備え（2026-09-30 第 2 巡）: 1 回の適用で扱う編集は新しい 1,000 件まで、受け付けられるものからの
  適用し直しは 8 周まで（原稿の版は節・版番号の順に並べ直す）、1 つの節へ Cookie から戻せる版は 200 版まで、
  Cookie から戻す版 1 件の本文は正規化した JSON で 20 万字まで、1 回の適用で組み立て直す本文・写しは合わせて
  100 万字まで（実演の流れの終わりで約 1.3 万字）。スナップショットの目録は重複した節・行と件数の上限を超えるものを
  組み立てる前に止める。確定版の完全性は目録の基準の一覧ではなくプロジェクトの基準の行と適用判断の記録で見て、
  作成日時はプロジェクトの作成と各節の最終承認の後・未来でないこと。ID を変えながら新しい行を足し続ける偽の Cookie で
  共有のメモリが増えること自体は、ほかの持ち回す表（コメント・通知など）と同じく残る（デモのアカウントは誰でも使える前提。D-4）。

#### 報告年度・収集キャンペーンも Cookie で持ち回す（2026-10-07・UI 再設計の検証 F1）

組織・拠点の「報告年度」「収集キャンペーン」の作成は、保存のあと結果の通知付きの画面へ移る（Server Action の redirect。
移った先の描画は別のリクエスト）。`periods`・`campaigns`・`campaign_scopes` を持ち回していなかったため、移った先が別の
インスタンスに届くと「追加しました」と出るのに一覧に行が無かった。3 表を Cookie の対象に加えた（年度・キャンペーンは
1 回の操作で 1 行。収集スコープは組織 × 指標の行で、同じ ID の繰り返しが多く圧縮が効く）。
`tests/e2e/zzzz-master-create.stateless.ts`（stateless の構成だけ）と `tests/integration/ui-redesign-review-actions.test.ts` が確かめる。

- キャンペーンが起こすタスク（`tasks`）は持ち回さない（従来どおり、別インスタンスではワークフローのタスクに出ない）。
- 組織 × 指標の多いキャンペーン（例: 全拠点 × 数十指標）は Cookie の容量を多く使い、古い操作から押し出す
  （押し出しはヘッダーの印で示す。ほかの大きな操作と同じ）。

#### CSRD の編集も Cookie に依存する（2026-10-01・docs/disclosure-first.md §9.3）

CSRD の 6 表（`csrd_analysis_settings`・`csrd_dma_matters`・`csrd_dma_iros`・`csrd_assessments`・`csrd_action_plans`・
`csrd_disclosure_drafts`）と、CSRD の収集項目が作る割当（`metric_assignments`）を Cookie で持ち回す。
CSRD の編集が別インスタンスで残るのは、この Cookie があるあいだだけ（同じブラウザで操作する。8 時間で失効・押し出しあり）。

- 差分だけを記録する。FY2026 の評価 12 行は Fixture に全部置き、**表示で行を作らない**（読込関数は一切書かない。
  行の無い期間は既定値の仮想行として読み、最初の保存で決定的な ID の行を作る）。SSBJ の評価行の一括作成のように
  初回表示で Cookie を使い切らない。
- CSRD の AI の実行（ギャップ分析・草案）は、出力（`output_json`）を空にして載せる。出力は評価の `ai_*` 列・節の `ai_body` に
  写し終えており、画面はそちらを読む。草案（デモ生成）は 1 節 600 字以内、人の本文は 3,000 字まで（1 件で Cookie 1 つ分を超えない）。
- 戻すときは DB と同じ規則を通す（`src/lib/repositories/demo-csrd-checks.ts`）: 期間・事項・評価・指標・拠点が同じ組織のもの、
  書いた人・判断者・確認者・確定者が権限を持つ、CSRD の要求事項だけ（ガードトリガと同じ）、業務キーの一意、形の CHECK
  （根拠必須・IRO の形・確認なしの最終判定・本文なしの確定）、既にある行の組織・期間・親を書き換えない。
  **DMA の確定は、戻した事項の判断で確定の条件を確かめ、満たさなければ確定だけを外して受け付ける**（事項の判断が
  押し出されたときに、報告範囲・閾値の変更まで捨てない）。AI の実行が押し出されて無い評価・節も受け付ける（他組織の実行は拒否）。
- 開示デモのリセットは CSRD の 6 表と CSRD の AI の実行も初期値へ戻す。CSRD の計画から作った収集項目も戻す（計画が結び付けた
  指標の Fixture に無い割当・計画から新しく作った指標（数値の行が無いもの）を消し、収集項目の作成が補った指標の担当部署・証跡必須を
  Fixture の値へ戻す。Cookie からも外す）。SSBJ の計画も結び付けている指標は、どちらの計画の収集項目か区別できないため触れない。
- CSRD の AI の実行は、Cookie では参照元（`source_references`）と入力の参照（`input_reference_ids`）も空にして載せる
  （別インスタンスの画面は提供元・モデル・Prompt 版・確信度・注意・状態だけを使う。メモリの行は全体を持つ）。
- 人の操作 1 回の書き込みで、通常の圧縮（Brotli 品質 9）では Cookie に収まらないときだけ、強い圧縮（品質 10。約 5〜6% 小さく、
  約 10 倍遅い 9ms 程度）を 1 回試してから古い操作を押し出す（取込の行の書き込みでは使わない）。
- 実測（`tests/integration/csrd-demo-persistence.test.ts`、操作ごとに Fixture を作り直す最悪の場合）: §9.7 の CSRD の流れ
  （G1 の判断 → DMA 確定 → AI 分析と採用 → 計画 → 収集項目 → 草案の生成・採用・保存・確定）の終わりで操作の記録は約 3.3KB、押し出しなし。
- 実測（`tests/integration/stateless-demo-chain.test.ts`、2026-10-01 自己監査 F1）: §8.6 の実演の流れ（約 8.5KB）の後に同じブラウザで
  CSRD の流れを続けても約 11.0KB（上限 11.4KB）で押し出しなし。前半の確定版（承認済みスナップショット）・DOCX の出力記録・CSV の数値の版・
  CSRD の DMA 確定と草案の確定がすべて別インスタンスに残る（逆の順でも押し出しなし）。以前は CSRD の AI の実行の参照元（実行 1 件で約 2〜3KB）で
  上限を超え、前半の CSV の数値の版が押し出されて確定版と出力記録が別インスタンスで消えていた。余裕は小さいため、実演で手順を足す
  （IRO の追加・分析のやり直し・取込など）と押し出しが起き得る（デモの帯で知らせる）。
- 実測（E2E `tests/e2e/zzz-csrd-chain.spec.ts` を `pnpm test:e2e:stateless` で。リクエストごとに Fixture を作り直す、2026-10-01）:
  同じ流れを画面で通して 9 件合格。Cookie ヘッダーの最大 4,077B（操作の記録 3,948B = 3,800/148。草案の確定の後）、押し出し 0。
  この spec は前の spec の Cookie を捨てて初期状態から始め（`resetCarriedDemoState`）、最後に開示デモのリセットで戻す。

#### 開示優先モード OFF でも見える Fixture の差（REG-F5・対応見送り）

開示優先モードの架空データは共通の Fixture に入っているため、機能を OFF にしても次の差が従来画面に現れる。

- Data Room の HQ Scope1 に第 2 版（再確認の題材）がある。
- ホームの「最近の操作」と Evidence 一覧に、開示優先モードの架空資料・操作が並ぶ。

これらを OFF 時に隠すと、再確認の筋書き（元データの訂正 → 原稿が「再確認が必要」になる）と、承認済みスナップショット
（SNAP-1）の数値の整合が崩れるため、Fixture を分けない。架空データであり、実顧客データは含まない。

**残る制約**: 本番 Demo Mode のプレビューは**投入したタブでのみ**参照できる。
別のブラウザ・別のタブ・タブを閉じた後は表示できず、理由を説明する画面を出す
（存在秘匿のため、取込直後以外の未知 ID は 404 のまま）。
評価・コメント・値編集などの小さな操作は引き続き Cookie でも持ち回している。
Supabase Mode では DB を共有するため、これらの制約は無い。

## 6. Migration のロールバック方針

- **破壊的マイグレーションを行わない。** `DROP TABLE` / `DROP COLUMN` / 型の縮小変更は禁止。
- 列の廃止は「使用停止 → 一定期間後に削除」の 2 段階とし、削除は別リリースで行う。
- ロールバックは「打ち消す新しい migration を追加する」方針（`supabase/migrations` は追記のみ）。
- 適用前に必ず `pnpm test:rls` を通す（PGlite に対して全 migration を最初から適用するため、
  順序依存の破綻を検出できる）。
- Seed は `pnpm seed:generate` で再生成する。手で編集しない。

`pnpm audit` の結果は `AI_HANDOFF.md` に記録しています。

### uuid（exceljs 経由・moderate 1 件を受容）

`pnpm audit --prod` は `.>exceljs>uuid` に GHSA-w5hq-g745-h8pq（moderate）を報告する。
**受容する。** 理由:

- 指摘は uuid の **v3 / v5 / v6 に `buf` 引数を渡したときの境界チェック漏れ**。
- exceljs が使うのは `v4` だけで（`lib/xlsx/xform/sheet/cf-ext/cf-rule-ext-xform.js`）、`buf` 引数も渡さない。
- 修正版の uuid 11 以降は **ESM only** のため、CommonJS の exceljs が `require('uuid')` に失敗する。
  実際、`uuid: '>=11.1.1'` を全体へ適用していた間、**Vercel 上で Excel の取込が PROCESSING_FAILED で全滅していた**
  （ローカルの vitest / dev は ESM 解決のため再現しない）。
- そのため `pnpm-workspace.yaml` で `exceljs>uuid: '8.3.2'` を固定している。exceljs 以外は 11 以降のまま。

代替（exceljs を ESM 対応ライブラリへ置換）は影響範囲が大きいため Phase 2 以降で検討する。

## 10. Framework の不具合とその回避（Next.js 15.5.23）

### 症状

Layout と Page の間に **Suspense 境界**（`loading.tsx`、または Layout 内で `{children}` を
`<Suspense>` で包む書き方）があると、Client 側の遷移（`<Link>` クリック）が確定しないことがある。

- RSC Payload はサーバーから **200 で完全に返っている**（本文も欠けていない）
- それでも URL が変わらず、画面も切り替わらない
- Console エラー・CSP 違反・ネットワークエラーは一切出ない（**無言で固まる**）

上流 Issue: https://github.com/vercel/next.js/issues/86151

### 本アプリでの再現条件

`/assurance/engagements` から `/assurance/engagements/[engagementId]/overview` への
遷移で **100% 再現**した（Supabase Mode・本番ビルド）。Demo Mode では
サーバー応答が速いため間欠的にしか出ず、E2E を通しで流したときだけ落ちていた。
上流 Issue のとおり「ページの描画が重い／Payload が大きいほど出やすい」挙動と一致する。

### 回避策

`src/app/enterprise/loading.tsx` と `src/app/assurance/loading.tsx` を**削除**し、
Layout 内にも `<Suspense>` を置かない。Layout 内 `<Suspense>` でも同じように固まることを
実機で確認済みなので、**loading.tsx を Suspense へ置き換えるだけでは回避できない**。

トレードオフは S-11 のとおり（遷移中のスケルトンが出ない）。PC 前提の社内システムで
サーバーが同一 VPC 内にある想定のため、Phase 1 では許容する。

### 回帰検出

`tests/e2e/vertical-slices.spec.ts` の `Client 側遷移` describe が、
企業・監査法人の両ワークスペースで「未訪問ルートへの `<Link>` クリックで URL と本文が
切り替わる」ことを検証する。Loading 境界を復活させるとここが落ちる。

### 解消の見込み

Next.js 16 系で修正 PR（vercel/next.js#95391）が取り込まれている。
16 へ上げる際は、この回避策を外して上記 E2E が通るかを最初に確認すること。

## 12. UI 再設計（2026-10-07。docs/ui-redesign/plan.md）の制約

- **端末ごとの保存**: 利用者の保存ビュー・既定ビュー・最近使った画面・左メニューの開閉・「はじめに」を閉じた印・表示件数の好みは、ブラウザの localStorage（`t4d.*.v1.<利用者>:<組織>`）にだけ置く。別の端末・別のブラウザには引き継がれない。共有したいときは URL をコピーする（列・絞り込み・並べ替えはすべて URL に載る）。プライベートモードなどで保存できない環境でも、画面は同じに描く（保存だけをしない）。

### 13.1 Demo Mode（Cookie で持ち回すもの・持ち回さないもの）

- **「要再確認」の通知は保存しない**: ホームの Attention と通知センターの「要再確認（上流の変更）」は、自分が担当の節・最終承認者のプロジェクトの節を表示のたびに調べる（既読の管理は無い）。節ごとに鮮度を計算するため、節の多いプロジェクトでは重い（件数だけをホームに出す）。
- **Cookie の予算（plan K8）**: 試行の流れ（`tests/integration/stateless-trial-chain.test.ts`）の最大は約 3,950B（上限 9,000B）、実演の流れ → リセット → 試行の流れの最大は約 5,700B、実演＋CSRD の流れの最大は 11,099〜11,145B（実行ごとに ID・時刻で数十 B 揺れる。回帰の上限 11,200B。出力記録の突合の 3 件を 1 つの配列にまとめた）。押し出しはどれも 0。
- **実演＋CSRD の流れの後の余裕は約 300B**: その後に Cookie へ載る操作（XBRL の AI 候補は対応付けの候補の行で約 1.3KB、要求事項の AI 候補は約 0.8KB）を続けると、いちばん古い操作（取込の数値など）が押し出される（押し出しは通知で知らせる設計。D-3）。AI の実行は読み直す列だけを載せる（XBRL の候補は出力・参照元を省き、要求事項の候補は入力の参照を先頭だけにする）。実演の流れの後に両方の候補を出しても押し出しは 0（`stateless-trial-chain.test.ts`）。
- **開示デモのリセットの範囲**: トライアルの評価の記録（計画・実施記録・判定・ご意見・作業時間）・AI 候補の不採用の理由・承認ルートと段階・データ取扱条件の版・メンバー（担当拠点）・CDP の対応付けと回答の紐付けも、組織の範囲で Fixture の値へ戻す。監査法人が書いたコメント（`review_notes`）は企業のリセットでは消さない・戻さない（保証側の記録。写しが消えたコメントは「写しが見つかりません」と出る）。リハーサルで保証側のコメントを書くと、そのコメントだけは Cookie に残る（1 件あたり約 0.5KB）。
- **承認ルートの保存**: 同じ名前の経路は新しく作れない（「編集」から変える）。段階は変わった段階だけを作り直し、同じ中身のまま保存し直しても行を増やさない。3 段階のひな形は既定に入れない（既定にするのは人が選ぶ）。
- **監査ログは持ち回さない**: 監査ログ画面は「同じインスタンスで発生した記録と架空の記録だけ」（画面に表示）。Data Room の「前回表示以降」の選択肢は、同じインスタンスで前回表示したときだけ出る（URL の `?since=` は常に効く）。
- **役割の変更は同じインスタンスのメモリだけ**: `membership_roles` は主キーが無く持ち回さない（画面にも注記）。担当拠点・利用の停止は架空メンバーについて持ち回す。Demo のログイン利用者は変更できない。
- **持ち回すようにしたもの（Stage C）**: CDP の質問と指標の対応付け（`disclosure_mappings`。確定・追加・外す）。戻すときは CDP の質問・同じ組織の指標・書き手の編集権限・確定者の本人名義・一意を検査する。同じセッションで付けて外した T4D の情報の対応付けも、外した状態で戻す。
- **回答の承認の職務分離の戻しの検査**: Cookie は行の最後の形だけを持つため、Demo の戻しでは「現在の版を作った人が承認者でない」ことだけを見る（DB のトリガ 0057 は承認者＝書き手本人も見る）。回答の版（`disclosure_response_versions`）は持ち回していないので、版が戻らない回答は見ない。
- **シナリオ定義**: `trial_scenarios` は Fixture だけ（画面での追加・編集は無い。運営が Supabase で入れる前提）。
- **提出者の識別子**: Demo では読み取り専用（識別子を Cookie に載せないため）。Supabase Mode は企業管理者が保存できる（E2E は無い。integration で固定）。

### 13.2 要求事項・対応表・トレース・出力

- **ESRS-40a はサンプル**: FY2026 の 40a は「試行用サンプル（架空・条文ではない）」の 8 項目。公開草案の版は要求事項を収録していない（プロジェクト設定タブに「公開草案（未収録）」）。草案・サンプルの基準は「充足確認済み」にしない（上限は「追加確認が必要」）。
- **横断対応表はサンプル 6 件**（SSBJ ↔ 40a）。CSRD の架空 12 項目への対応は作っていない。AI の対応候補は表示だけ（横断のマスターに書かない）。
- **追跡は節単位**: 段落単位の要求事項の対応付け（NF-45）は先送り。FY2025 の Fixture の承認済みスナップショットには引用位置（出典印）が無く、追跡率は 2 / 5（段落 1 / 4・数値 1 / 1）。
- **保証側の追跡**: 写しに定性情報の根拠（引用位置）の有無を持たないため、定性情報の引用だけを根拠とする段落は保証側の追跡で「根拠なし」と数える（画面に断り書き。FY2025 の Fixture には該当なし）。
- **突合**: T4D が作った DOCX・XLSX・CSV を読み戻して承認版と照合する（公式の検証・第三者保証ではない）。不一致が 1 件でもあればファイルを渡さず記録だけを残す。外部で編集したファイルは保存せず、sha256 と結果・明細（Demo 5 件・Supabase 50 件）だけを記録する。
- **「要再確認」の絞り込み**: 要求事項タブの「要再確認」は、数値・定性情報の新版に加えて資料の新版・失効した根拠も数える（概要の「上流の変更で再確認が必要な節」と同じ集合）。資料の新版は再確認の判断（`recheck_decisions`）に記録できないため、区分（5 区分）と承認の可否には使わない。
- **ドラフトの取り込みの AI 由来の印**: SSBJ・CSRD のドラフトから取り込んだ段落の AI 由来は段落 ID の接頭辞（`draft-ai-`）で残す（原稿の AI 下書きの `aiRunId` とは別。検査の対象が違うため）。
- **SSBJ の基準の版**: 年度の版は設定の確定時に固定する。固定していない年度は公開中の版を読む。SSBJ の DOCX の「基準」・定量指標・CDP 形式の出力（`/api/exports/cdp?framework=ssbj`）も同じ版を読む（`?version=` を付けたときだけ別の版）。
- **SSBJ の整備度の分母**: 対象外・非重要は、理由があり申請者・理由を記録した人と別の人が承認したものだけを分母から外す（全体状況・ホームの見出し・要求事項の整理）。承認待ち・未申請は未判定として分母に残し、全体状況に件数を出す。
- **SSBJ の「理由を記録した人」**: 適用区分・重要性とその理由を最後に記録した人（`reason_recorded_by`。0059 より前の行は最後に更新した人）。この人は対象外・非重要を承認できない（差し戻しはできる）。
- **要求事項の状態のダイジェスト**: SSBJ の評価行が無い要求事項と、システムが作った既定のまま（適用・重要性未判定・理由なし・最終判定なし）の行は同じものとして扱う（画面を開いて既定の行が作られただけで「確定後に変更あり」にしない）。0059 より前の Supabase のスナップショットが既定の行を含めて固定したダイジェストは、比べ直すと「変更あり」になりうる（Supabase Mode は未運用）。
- **承認版どうしの差分**: 片方が判断の状態を固定する前の形式（v1）のときは、判断の違いを比べず「違いはありません」と言わない（画面に断り書き）。
- **突合の照合規則 v2**: DOCX は表紙から末尾まで照合し、期待値に無い段落（節の末尾・表の前後・末尾に足した記述）・期待値に無いシートを余分として数える。照合した段落・数値・行が 0 件のときは「照合対象なし（一致の判定なし）」と示す。外部で編集したファイルの大きさは、XLSX は期待する行・列の 2 倍程度まで（寸法だけ巨大なシートは読まずに断る）、DOCX は本文の展開後 32MB まで。

### 13.3 保証連携

- **資料の実体の閲覧（保証側）**: アプリ層の判定（`canReadEvidence`）を DB と同じ規則にした: Data Room の行（許諾×承認の導出。企業の取り下げの記録を守る）の Data Point に紐付く資料で、その指標の許諾が Evidence を含むもの、または共有中の開示レポートの写しが引用する資料の版（許諾が Evidence を含むとき。0050）。
- **写しの伏せ字**: 非公開資料の名前・引用文は写しに載せない（対外用と同じ。§5 の判断事項 D3 が決まるまで）。
- **指摘（`assurance_issues`）の企業側の表示**は無い（判断事項 D4 の後）。
- **保証側の閲覧の記録は企業の監査ログに出ない**: Data Room・共有した開示レポートを表示した記録（`record_viewed`）は監査法人の監査ログに残る（監査ログの読み取りは記録した組織の範囲）。企業が辿れるのは資料のダウンロード・閲覧（`storage_access_events`）だけ。
- **共有の写しはサーバーが作る**: 写しの内容とハッシュは利用者の JWT では書けず（0059）、Supabase Mode の共有は Service Role で書く（権限・許諾・承認版の検査の後）。取り下げた写しは保証側から読めない（SELECT ポリシー）。Sign-off に結び付けた写しが取り下げられると、保証側には「取り下げられた写し」と出る。
- **開示回答の承認（0057・0059）**: 承認と同じ更新で版を差し替えること・版と違う本文の承認・版を外すことは DB で断る。過年度の回答の取込（過去回答 Import）は版を作らずに承認済みの本文を書き込むため、承認済みの回答の本文を後から書き換える操作は DB では区別できない（アプリの取込だけが行う）。

### 13.4 CDP 対応オプション

- 契約は運営が設定する（`organization_options` は顧客が書けない。Demo でも書く関数を置いていない）。契約の無い組織では、CDP の画面は「契約されていません」の理由を出し（404 にしない）、メニューの CDP の葉・パレットの CDP の画面と質問の検索・レポートの CDP のカードを出さず、出力 API は 403、Action・適用判定・質問マッピング・過去回答の取込（資料を保存する前）・規制対応度の CDP 行は止める。
- CDP の回答の承認は単段＋職務分離（3 段階は判断事項 D10 の後）。CSRD の回答も同じ関数のため、作成者は承認できない。
- 回答の根拠の紐付けは追記だけ（外せない）。期間の版は「期間の開始の年と同じ年の版、無ければ公開中の版」で導く（記録しない）。
- CDP の正式質問票（気候変動）は収録していない（§4 M-1。ポータル登録とライセンス確認待ち）。CDP ポータルへの送信・API 連携は行わない。

### 13.5 XBRL（Stage 1 のみ）

- 社内確認用の構造の確認で、**提出用ではない**（画面・出力の先頭に「提出用ではありません」）。タクソノミは SAMPLE（架空。名前空間 `urn:t4d:sample-taxonomy:2026`）で、公式タクソノミ（EDINET・ISSB・ESRS）は同梱しない。検証 V01〜V16 は T4D の簡易検査で、公式の検証ではない。
- scale は単位から自動（対応付けの scale は Stage 1 では使わない）。
- Stage 2〜3（公式タクソノミの読込とライセンス、EDINET の規則、公式の検証器、版差分と対応付けの引継ぎ、段落・範囲単位の詳細タグ、保証側の閲覧、前年・基準年の版の固定）は今後。

### 13.6 トライアルの評価・管理

- トライアルの記録の画面は Demo Mode で「架空のトライアル記録です。実測値・実際の効果ではありません。」を常に出す。率・短縮率は件数（n）と測り方を併記し、件数が足りなければ数値を出さない。費用対効果は試算（入力は URL だけで保存しない）。
- 短縮の目標は計画の任意の設定（Fixture には無いので「目標は未設定」と出る）。
- 概要の件数（定量指標・年度）は、Supabase Mode の PostgREST の既定の上限（1,000 行）により、データ点の多い組織では少なく数えうる（拠点を指定すれば DB 側でも絞る）。
- 監査ログ画面の「最終ログイン」は組織を選んだ記録（`workspace_selected`）。ログインの記録は組織を持たず RLS で企業から読めないため。
- 全データの返却書き出しは、Supabase Mode では非公開バケット `tenant-exports-private` に Service Role で置き、利用者の権限で署名 URL（10 分）。E2E は Demo の直接返却だけを確かめている。
- `api/files/download` の案件の記録は、案件のメンバーが開いたときだけ（企業の利用者の取得は案件に結び付けない）。
- テナントの終了（削除）は手順書（`docs/operations/tenant-offboarding.md`）と保守関数 `t4d.offboard_organization`（所有者だけが実行）で行う。画面からは行わない。バックアップ・復旧は手順書だけで、画面に推測の「最終バックアップ日時」は出さない。
