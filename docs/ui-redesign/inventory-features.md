## 7. 自動到達性チェックの戦略

### 7.1 静的: すべての Server Action が UI から呼ばれる（`tests/unit/server-action-reachability.test.ts` 案）

1. `typescript`（devDependency 済み）の AST で `src/**/*.{ts,tsx}` を走査し、先頭が `'use server'` のモジュールの export 関数を列挙する。
2. `'use server'` でない `src/app/**`・`src/components/**` のモジュールの `ImportDeclaration` を、`@/` と相対パスを解決して照合する。取込元ファイル内でインポート以外の参照（`action={X}`・`formAction={X}`・`useActionState(X…)`・`X(`）が 1 回以上あることまで確かめる（import だけの死にコードを拾わない）。
3. 期待: すべての export が 1 つ以上の UI モジュールから参照される。例外は**理由付きの許可リスト**だけ（初期値: F136〜F144。F048・F121 は「UI を作る／削除する」を決めるまで許可リストに入れず失敗させるか、`DECISION_PENDING` として件数固定で検査する）。
4. 追加の不変条件: `'use server'` モジュールの export 名は `…Action` で終わる（getSelectedPeriodId を検出）。
5. 7.2 の到達グラフと合成し、「取込元コンポーネント → それを描画するページ → そのページが到達可能」まで確認する（Action は残ったが置き場のページが孤立した、を検出）。

### 7.2 静的＋E2E: すべてのページがメニュー・⌘K・画面内リンクのいずれかから到達できる

**静的（`tests/unit/route-reachability.test.ts` 案）**

1. ルート表: `src/app/**/page.tsx` → パターン（route group 除去、`[x]` は 1 セグメント）。
2. 入口: `navTreeFor('enterprise')`・`navTreeFor('enterprise-disclosure')`・`assuranceNav('<uuid>')` を import して全 href を集める（⌘K は同じ集合なので `navCommandEntries` の結果も同値であることを assert）。ヘッダー固定の `/notifications`・`/profile`・`/workspace` を加える。
3. 辺: 各ページから import グラフ（TS のモジュール解決）で到達する全モジュール内の、JSX `href`・`Link`・`router.push`・`redirect()`・`{ href: … }` のリテラル／テンプレート（ファイル内定数を展開、`${…}` は 1 セグメント）。`src/lib/services` のリンク生成も import グラフ経由でそのページに帰属させる。
4. モード別に BFS し、到達しないルートは `ENTRY_ONLY`（/login・/mfa・/reset・/invite/[id]・/・redirect 専用の /enterprise/analysis）か、**モード別の明示リスト**（従来: P26・P27・P35。§6.3）に理由付きで載っていなければ失敗。
5. 限界: 条件付き描画（例 imports/page.tsx:71 の `disclosureFirst &&`、権限分岐）は静的には見えない → 7.2 E2E で補う。

**E2E（`tests/support/crawl.ts` の拡張）**

1. 現状の crawl は `visited.length > 20` しか見ていない（screen-audit.spec.ts:38）。訪問したパスをルートパターンへ正規化し、**ルート表との差分**を出す。
2. 種はホーム 1 つだけ（深い URL を種にすると到達性の検査にならない）。メニュー・⌘K（`role=option` を列挙）・画面内リンクのクリックだけで辿る。
3. 行列: 役割（管 作 拠 レ 承、監査法人 P M S 法）× モード（従来／開示優先。ON/OFF は F113 を使い、テスト後に戻す）。期待集合は「ルート → 必要権限」の表（§2 の閲覧条件）から役割ごとに導出し、**期待集合 ⊆ 訪問集合** を assert。
4. 同時に「メニューに出た項目を開いて PermissionDenied にならない」（R5 を検出）と「表示された出力リンクが 403 にならない」（R3 を検出: リンクを `request.get` して status を確認）を assert。

### 7.3 静的: 画面の権限ゲート ⊆ サービスの権限（R1・R2・R4 の再発防止）

Action ごとにサービスまでたどった `assertCan` 集合（本書の抽出方法と同じ）と、その Action を置くコンポーネントの表示条件 `can(ctx,'…')` を突き合わせ、「表示条件を満たすがサービスで必ず拒否される役割」が存在すれば失敗させる。役割 × 権限は `ROLE_PERMISSIONS` から計算する。

### 7.4 E2E の網羅（既存 spec の対応と不足）

- **対応表**: `tests/e2e/feature-coverage.ts` に `F### → spec ファイル名とテスト名` を持ち、unit テストが (a) §3 の全 Action が表にあるか `NO_E2E_YET`（理由付き）にあること、(b) 参照先の spec・テスト名が実在することを検査する。§3 の E2E 列が初期値。
- **条件付き skip の扱い**: `test.skip((await x.count()) === 0, …)` が 36 か所（action-audit 11・interaction-audit 7・business-flow-audit 5・edge-cases-audit 4・tenant-isolation-audit 4・crud-persistence 3・security-audit 1・write-paths 1）。UI 再設計で操作を L2（ドロップダウン・アコーディオン・行メニュー）へ移すと、**失敗ではなく skip になり緑のまま**になる。回帰チェックの実行では Playwright の結果で skipped > 0 を失敗扱いにするか、前提データを fixture で保証して `expect(count).toBeGreaterThan(0)` に置き換える（期待値は緩めない）。
- **E2E が無い機能**（再設計で壊しても気づけない）: F025・F044・F048・F049・F050・F055・F074（実行）・F080・F081・F082・F083・F084・F085・F086・F087・F095・F097・F101・F104・F121、出力 E03。ページでは P27・P42・P59（scope）・P61（population）・P76・P77 がリテラル 0（P59・P61 は crawl のみ）。優先度は開示優先の作成系（F082〜F087）と目標登録（F104）が高い（再設計の主対象で、かつ未検査）。
- **ラベル依存**: 既存 E2E は `getByRole('button', { name: '…' })` で操作を特定している。ラベルを業務用語へ言い換える場合は §3 の「操作ラベル」列を新旧対応表として使い、spec を同じコミットで更新する（「Changed」の判定根拠）。

### 7.5 回帰判定の手順（最終報告で使う）

1. 7.1・7.2（静的）・7.3 を `pnpm test` に入れる。
2. 再設計の各段階（Navigation → Layout → Component → Table → Form → Contextual Action → Advanced）の後に 7.2 E2E を役割 × モードで実行し、§2・§3 の ID ごとに Missing／Broken／Changed／Unreachable を記録する。
3. 基準線は本書 §6。§6 に無い項目が新たに到達不能になったら回帰。§6 の項目を直した場合は本書を更新する。
